Large-Scale Soundscape Training Data — a build plan

Generating millions of richly-annotated multilingual soundscapes to pre-train a single model that replaces the LAION Universal Audio Annotation Pipeline (UAAP) ensemble. v1 · for engineers new to the project.

TL;DR. We already built a 200-clip benchmark (SoundScape-Bench) by gluing "understood" audio pieces (speech, sound effects, music, vocal bursts) onto a timeline so that the exact answer key is known by construction. This document scales that idea to millions of clips across ~50 languages (everything VibeVoice-ASR supports), with overlapping speech, ducked backgrounds, procedural loudness, and cross-lingual same-speaker tricks — formatted in the UAAP JSON schema. The end goal: pre-train one audio-LLM to emit the whole UAAP annotation in a single pass, then fine-tune it on the ensemble's predictions, so we no longer need the slow multi-model ensemble. Below: the data sources & their exact fields, the sampling/captioning/mixing algorithms with code, two compute architectures (CPU swarm vs. supercomputer), the output format, the downstream model design, and a licensing matrix.

1. Background — what is UAAP and why build this?

The Universal Audio Annotation Pipeline (GitHub) listens to any audio clip and emits a single structured JSON list describing everything audible, second by second: who speaks, when, what they say, in which language, with what emotion / age / gender / timbre / speaking-style; every non-speech sound effect; the music; and little vocal bursts (laughs, sighs). Today it does this with an ensemble of ~8 models (VibeVoice + Nemotron ASR, pyannote/Sortformer diarization, DiCoW overlap ASR, Whisper "expert" caption models, an SFX detector, and a fusing LLM). That's accurate but heavy and slow.

The plan in one sentence: manufacture a huge, perfectly-labelled training set of synthetic-but-realistic soundscapes, use it to pre-train one model to predict the UAAP output in a single forward pass, then distill the ensemble into it — replacing 8 models with 1.

Why synthetic soundscapes? Because if you assemble a clip from pieces you already understand (a known speech utterance + a known sound effect + known music), then you already know the perfect label — no human annotation, no ensemble needed for the ground truth. That is exactly how SoundScape-Bench was built; we are now industrialising it.

The established output format (memorise this)

Every clip is a JSON array of event dictionaries, one of four types. This is the UAAP schema the model must learn to emit:

// speech
{"type":"speech","start_time":2.31,"end_time":5.87,"transcription":"I can't believe you did that",
 "speaker_id":"speaker_1","language":"en","emotion":"clearly intense anger laced with disappointment",
 "age":"adult_30s","gender":"female","voice_timbre":"alto, warm, slightly raspy",
 "speaking_style":"confrontational bark, clipped","accent":"American Midwest","speaking_rate":"fast"}
// vocal_burst
{"type":"vocal_burst","start_time":5.87,"end_time":6.14,"speaker_id":"speaker_1",
 "vocal_burst":"scoff","emotion":"slight contempt with a flicker of amusement","transcription":null}
// sound_event
{"type":"sound_event","start_time":3.10,"end_time":5.20,
 "description":"Medium-sized dog barking aggressively in the background","loudness":"moderate"}
// music
{"type":"music","start_time":9.80,"end_time":15.10,
 "description":"Upbeat acoustic folk-pop: strummed steel-string guitar, light tambourine, ~110 BPM, warm",
 "loudness":"moderate"}

Per-clip wrapper used by the benchmark: {"clip_id","duration","num_speakers", "languages":[...],"events":[...]}. Times in seconds; loudness ∈ {very_quiet, quiet, moderate, loud, very_loud}; speaker_id is consistent within a clip; events may overlap.

2. What we already did — SoundScape-Bench (200 clips)

Three scripts, run once on one GPU box. This is the seed recipe we are scaling.

collect_pools.py bud_e_caption.py build_soundscapes.py ───────────────── ────────────────── ──────────────────────── stream source HF → caption "how it's said" → glue pieces on a timeline → clip_NNN.mp3 datasets, 1 shard per speech snippet with (bg music/sfx + speech turns clip_NNN.json at a time; save BUD-E-Whisper_V1.21 + vocal bursts + fg sfx), (EXACT answer key) 16 kHz wavs + JSONL RMS-mix, peak-limit, export
  • Pools (one JSONL per layer): speech (emolia EN/DE/FR, MLS ES/NL, Emilia ZH, 3–12 s, unique speakers), SFX (AudioSet-grounded captions, music/speech filtered out, 0.8–10 s), music (captioned-ai-music), vocal bursts (synthetic).
  • Mixing (build_soundscapes.py): durations spread 10–60 s; background = 60% music bed / 20% ambient-SFX bed / 20% silence; 1–3 speech turns; 25% overlap (2nd turn slides into the 1st); ~40% of turns get a vocal burst; 1–3 foreground SFX. Everything RMS-normalised per layer (speech 0.11, music bed 0.045, fg-SFX 0.075…), summed, peak-limited to 0.97, exported 16 kHz MP3.
  • Answer key written directly from the placement decisions — no model needed.

That benchmark now ranks 15 systems; the best single-pass-able config (Gemma-12B text fusion) scores Reward 0.253. (The benchmark answer keys are exact; the LLM fuser is only used by the pipeline we want to distill.)

4. Diversity & recipe sampling — guaranteeing varied soundscapes

A dataset is only as useful as its variety. If every clip is "two people talking over a music bed for 30 s", the model overfits that shape. So a soundscape is not built from fixed defaults — every clip first draws a recipe by sampling each diversity dimension from an explicit categorical distribution. The dimensions are (mostly) independent, so their product spans the whole space; a few dependency rules (below) keep the result physically sensible.

The five dimensions, each sampled per clip: (A) content-mix archetype (speech : music : sfx ratio), (B) duration band, (C) temporal density / silence, (D) overlap mode, (E) speaker configuration (incl. same-speaker-multilingual via voice conversion). Each table below sums to 100% within its dimension; tune the weights to taste.

4.A — Content-mix archetype (the speech : music : sfx ratio) — PRIMARY axis

Sometimes all three types should be ~equal; sometimes only one type is present; sometimes one type dominates with the others as light accents. The archetype decides this. The S/M/F columns are the target share of "active content" (by active seconds & event count) — realized as a budget the sampler fills.

4.F — Dependency rules (keep the physics sensible)

  • Speech-on-speech overlap requires DIFFERENT identities. A person cannot talk over themselves — so overlap mode for speech only fires when speaker config is multi-distinct or multilingual-distinct.
  • Same-speaker-multilingual ⇒ turns are SEQUENTIAL (overlap forced to none among those turns). Realized with Chatterbox voice conversion: pick a same-gender second-language utterance and convert it to the first turn's identity (§8), so one person "speaks" English then Dutch, never at the same time. This is the single most valuable cross-lingual signal in the set.
  • SFX and music may overlap anything freely (music bed under speech, an SFX stab during music, ambience under dialogue) — overlap mode there controls how many concurrent non-speech layers.
  • Music-only / SFX-only ⇒ no speaker config, no speech overlap; overlap mode instead layers the sound/music events. Speech-only ⇒ no bg layer, so "continuous bed" degrades to dense/spaced.
  • Background mode follows the archetype: music bed when music is present & continuous; ambient-SFX bed when sfx-dominant & continuous; otherwise silence — and "spaced" density injects explicit silence gaps the answer key must cover as quiet room-tone.

4.G — The recipe sampler (one call per clip, pure CPU)

ARCHETYPES = [  # (name, weight, speech%, music%, sfx%)
  ("balanced",14,.34,.33,.33), ("speech_dom",16,.70,.15,.15),
  ("music_dom",11,.12,.76,.12), ("sfx_dom",11,.12,.12,.76),
  ("speech_only",13,1,0,0), ("music_only",6,0,1,0), ("sfx_only",8,0,0,1),
  ("speech_music",8,.55,.45,0), ("speech_sfx",9,.55,0,.45), ("music_sfx",4,0,.5,.5)]
DUR   = [(("micro",5,10),18),(("short",10,20),32),(("medium",20,40),32),(("long",40,60),18)]
DENS  = [("dense",30),("spaced",40),("bed",30)]
OVL   = [("none",50),("light",33),("heavy",17)]
SPK   = [("single",30),("multi",38),("same_multiling",17),("multiling",15)]

def sample_recipe(rng):
    arch  = wpick(rng, ARCHETYPES)                       # A: speech:music:sfx ratio
    (band, lo, hi), _ = wpick(rng, DUR);  dur = rng.uniform(lo, hi)   # B
    dens  = wpick(rng, DENS)                              # C
    has_speech = arch[2] > 0
    spk   = wpick(rng, SPK) if has_speech else None       # E
    # D: overlap only meaningful with >=2 overlappable events; speech overlap needs distinct ids
    can_speech_overlap = spk in ("multi","multiling")
    ovl   = wpick(rng, OVL) if (can_speech_overlap or arch_has_layers(arch)) else "none"
    if spk == "same_multiling":  ovl = "none"             # F: no self-overlap; turns sequential (VC)
    if has_speech and arch[1]==1 and dens=="bed": dens = rng.choice(["dense","spaced"])  # speech-only: no bed
    return dict(archetype=arch[0], ratio=arch[1:4], duration=round(dur,2),
                density=dens, overlap=ovl, speakers=spk, vc=(spk=="same_multiling"))
# the mixer (§9) then allocates each type's active-time budget per `ratio`, places events per
# `density`/`overlap`, assigns identities per `speakers`, and (if vc) routes turns through Chatterbox.

6. Speech sampling strategy

Two requirements pull in different directions — language balance (don't let English dominate) vs. emotion diversity (the emotional corpora are English-heavy). We satisfy both with a 50/50 split per speech slot:

For every speech utterance placed into a soundscape, flip a coin:
• ~50% "balanced" track — sample a language uniformly at random from the ~50 VibeVoice-ASR languages, then draw a clip for that language from majestrino common-voice (primary) ∪ Emolia (for languages/emotions CV lacks, e.g. emotional ZH/JA/KO) ∪ MLS (de/nl/fr/es/it/pt/pl top-up). This makes the long tail of languages appear roughly equally.
• ~50% "emotional" track — sample from emolia-balanced-5M-subset + laions_got_talent + the majestrino common-voice emotional captions. Mostly English/German but spanning ~40 emotions, giving the model strong affect supervision.

VibeVoice-ASR target language set (51): en, zh, es, pt, de, ja, ko, fr, ru, id, sv, it, he, nl, pl, no, tr, th, ar, hu, ca, cs, da, fa, af, hi, fi, et, am, el, ro, vi, bg, is, sl, sk, lt, sw, uk, kl, lv, hr, ne, sr, tl, yi, ms, ur, mn, hy, jv. Use this list as the uniform-sampling domain; fall back to the nearest available corpus per language.

Speaker uniqueness & dedup. Keep a per-run Bloom filter of used (source, clip_id) so no snippet is reused, and prefer distinct speaker ids within a clip. Filter to 2–14 s utterances with non-empty transcripts and decent quality (e.g. Emolia dnsmos > 2.5).

8. Cross-lingual same speaker — Chatterbox voice conversion

We want clips where one identity speaks two languages (e.g. an English then a Dutch turn) — a hard, realistic case. We can't get the same real person in two languages, so we synthesise identity with Chatterbox VC (ResembleAI/chatterbox, MIT): pick a same-gender second utterance in another language, then convert its voice to a fixed target identity, so both turns share a timbre.

from chatterbox.vc import ChatterboxVC
vc = ChatterboxVC.from_pretrained("cuda")
# turn 1: english clip from speaker A (its own audio becomes the identity anchor)
# turn 2: dutch clip from a DIFFERENT same-gender speaker -> convert to A's voice
converted = vc.generate(audio=dutch_clip_wav, target_voice_path=english_clip_wav)  # 24 kHz
# now both turns sound like the same person; ground-truth speaker_id is shared
Overlap rule (important): a soundscape may have overlapping speech only between DIFFERENT identities. If a clip uses the same-speaker-two-languages trick, those turns must be sequential, never overlapping (a person can't talk over themselves). Overlap ⇒ ≥2 distinct speaker_ids.

9. The soundscape mixer — overlap, ducking, procedural loudness

A pure-CPU procedural step (no GPU). Extends build_soundscapes.py. Key additions vs. the benchmark: a full overlap matrix, side-chain ducking (lower background under speech), music-with-foreground-intrusion, and a loudness ladder derived from the actual mix gain.

The loudness ladder (procedural → label)

Loudness is decided by us as a target RMS gain, then mapped to the UAAP label — so the label is ground-truth, not estimated:

LOUD = {"very_quiet":0.020,"quiet":0.040,"moderate":0.075,"loud":0.12,"very_loud":0.18}
def place(buf, audio, start_s, gain, SR=16000):
    a = rms_norm(audio, gain)                      # set this layer's RMS to the chosen gain
    o = int(start_s*SR); buf[o:o+len(a)] += a
    return a                                        # label = the key whose value == gain

Overlap matrix (what may sit on top of what)

over speechover musicover SFX
speech✓ if different speaker (duck nothing; both ~equal)✓ music ducked −6…−12 dB under speech✓ SFX ducked
SFX✓ (background bed, or a foreground "stab")✓ a non-musical stab during music✓
music✓ bed under speech; or loud with a sudden speech/SFX intrusion—✓

"Procedurally determined" cases the user asked for: SFX overlapping music; SFX overlapping speech; speech over a quiet music bed; loud foreground music suddenly interrupted by a speech turn or an out-of-place SFX stab (raise music to loud/very_loud, drop a moderate/loud speech or SFX event on top). Each placement writes its own ground-truth event with its own loudness.

Side-chain ducking (background gets quieter under speech)

def duck(buf_bg, speech_spans, SR=16000, atten_db=-9, fade=0.25):
    g = np.ones(len(buf_bg), dtype=np.float32)
    k = 10**(atten_db/20.0)
    for (s,e) in speech_spans:                       # lower bg during each speech span (with fades)
        i,j = int(s*SR), int(e*SR)
        ramp = int(fade*SR)
        g[i:j] = k
        g[max(0,i-ramp):i] = np.linspace(1,k,min(ramp,i))
        g[j:j+ramp] = np.linspace(k,1,min(ramp,len(g)-j))
    return buf_bg * g

Clip assembly (sketch — one CPU worker, no GPU)

def build_clip(rng):
    D = rng.uniform(5, 60); total=int(D*SR); buf=np.zeros(total, np.float32); ev=[]
    # 1) background: 55% music bed / 20% ambient-SFX bed / 25% silence
    r=rng.random()
    if r<0.55:
        m=draw_music();  a=place(buf, loop_to(wav(m),total), 0, LOUD[rng.choice(["very_quiet","quiet","moderate"])])
        ev.append(music_event(0,D,m))
    elif r<0.75:
        s=draw_sfx();    place(buf, loop_to(wav(s),total), 0, LOUD["quiet"]); ev.append(sfx_event(0,D,s,"quiet"))
    # 2) speech turns (1-3), 20-25% overlapping (different identities only)
    spans=[]; ids={}
    for turn in plan_turns(D, rng):                  # returns (start, clip, identity, do_vc, loud)
        a=wav(turn.clip);  a=maybe_vc(a, turn)        # cross-lingual same-speaker if requested
        place(buf, a, turn.start, LOUD[turn.loud]);  spans.append((turn.start, turn.start+len(a)/SR))
        ev.append(speech_event(turn))                # transcription/lang/emotion/speaker_id/... from source meta
        if rng.random()<0.4: ev.append(place_vocal_burst(buf, turn, rng))
    # 3) foreground SFX / music intrusions (some during speech, some in gaps)
    for _ in range(rng.choice([0,1,1,2,3])):
        s=draw_sfx(); loud=rng.choice(["quiet","moderate","loud","very_loud"])
        st=rng.uniform(0, max(0.1, D-dur(s)));  place(buf, wav(s), st, LOUD[loud]); ev.append(sfx_event(st,st+dur(s),s,loud))
    # 4) duck the background under speech, mixdown, peak-limit
    buf = apply_ducking_to_background(buf, spans)
    buf *= min(1.0, 0.97/(np.max(np.abs(buf))+1e-9))
    return buf, sorted(ev, key=lambda e:e["start_time"])

Sample rate: keep 24 kHz internally if you want crisper SFX/music, export 16 kHz mono MP3 for the speech-centric model (matches the encoders). Everything above is deterministic given the worker's RNG seed → reproducible clips.

10. Output format — UAAP-compatible, plus component files

Each generated clip emits three things so the heavy GPU annotation can be deferred and so the data is debuggable:

  1. clip_NNN.mp3 — the mixed soundscape (16 kHz mono).
  2. clip_NNN.json — the UAAP answer key (the event list from §1), plus a provenance block per event: {source_dataset, source_key, gain, raw_caption, needs_caption:true|false}. needs_caption=true marks events whose final caption must be written by the GPU/Gemma phase.
  3. clip_NNN_components/ — every source snippet as its own MP3 + its raw metadata JSON. This lets the GPU phase caption each piece in isolation (better than captioning the mix) and lets us re-mix or audit later.

11. Scaling to millions — the two-stage decentralized architecture

The recommended design splits the work along the hardware you actually have: one big storage/CPU server that owns every source dataset and does all sampling + packaging, and a decentralized fleet of GPU servers that fetch the packaged work and do the neural captioning + fusion + final mixdown. The two stages talk only through HuggingFace tar shards — no shared filesystem, no central scheduler.

┌──────────────────────────── STAGE 1 — STORAGE / CPU SERVER (24 cores, NO GPU) ────────────────────────────┐ │ all source datasets on local HD │ │ │ │ │ 24 worker processes (1 per core), each independently: │ │ 1. roll a soundscape RECIPE (balanced lang/emotion · duration · #turns · overlap? · bg · loudness) │ │ 2. draw the concrete pieces from the LOCAL datasets (dedup + per-language balance counters) │ │ 3. decode + resample each RAW component (16/24 kHz), gather ALL its source metadata │ │ 4. compute the full PROCEDURAL MIX PLAN (per-event start/end, gain, loudness label, duck spans, │ │ speaker_id, overlap flags, vc-needed) — this is the EXACT ground-truth skeleton │ │ 5. write ONE WebDataset row = { recipe.json + every component .flac + its .json } │ │ 6. pack 1000 rows → one .tar → push to HF (dataset repo: raw-soundscapes) │ │ CPU/IO only. No mixing, no neural nets. │ └───────────────────────────────────────────────┬───────────────────────────────────────────────────────────┘ │ HF tar shards (1000 rows each) ┌────────────────────────────────────────┼────────────────────────────────────────┐ ▼ ▼ ▼ ┌──── STAGE 2 — GPU server A ────┐ ┌──── GPU server B ────┐ ... ┌──── GPU server N ────┐ │ claim shards (hash-mod / lease)│ │ (different shards) │ │ (different shards) │ │ per row: │ │ │ │ │ │ GPU Whisper experts caption │ │ ── decentralized, no central scheduler; each server picks │ │ components missing meta │ │ disjoint shards by id and skips shards already done ── │ │ GPU Gemma-4-12B → UAAP dicts │ │ │ │ │ │ CPU render mixdown from the │ │ │ │ │ │ raw components per recipe │ │ │ │ │ │ → soundscape.mp3 + uaap.json │ │ │ │ │ │ push to HF (annotated repo)│ │ │ │ │ └────────────────────────────────┘ └───────────────────────┘ └──────────────────────┘
Why this division fits the hardware: the 24-core, GPU-less storage box is exactly right for Stage 1 — it's pure I/O + sampling + tar packaging, and it already holds the datasets (which are many TB). The GPU servers never touch the source datasets; they pull compact pre-bundled rows, so they spend 100% of their time on the captioners + Gemma + mixdown. Captioning the isolated component audio (not the mix) gives cleaner captions, and keeping the raw components in each row lets the GPU side re-mix, audit, or train the model on the separated sources later.

11.1 — Stage 1, in detail (CPU storage server, per worker)

StepWhat the CPU doesCost
a. roll recipeSample duration (5–60 s), #speech turns, the 50/50 balanced-vs-emotional track (§6), overlap decision (20–25%, different identities only), background type (music bed 55% / ambient-SFX 20% / silence 25%), #foreground SFX, #music intrusions. Pure RNG + counter bookkeeping.µs

# Stage-1 worker (1 per core × 24). All CPU.
import webdataset as wds, soundfile as sf, io, json
def build_row(rng, sources, counters, seen):
    rec = roll_recipe(rng, counters)                       # a,d: duration/turns/overlap/bg/loudness plan
    parts = draw_pieces(rec, sources, counters, seen)      # b: concrete clips, balanced + dedup
    row = {"__key__": rec["clip_id"], "recipe.json": json.dumps(rec).encode()}
    for role, p in parts.items():                          # role = spk0 / spk1 / sfx0 / music / vb0 ...
        a, sr = decode_resample(p["path"], target_sr=16000)  # c: raw component, no mixing
        buf = io.BytesIO(); sf.write(buf, a, sr, format="FLAC")
        row[f"{role}.flac"] = buf.getvalue()
        row[f"{role}.json"] = json.dumps(p["meta"]).encode()  # e: full source metadata
    return row
sink = wds.ShardWriter("raw-soundscapes-%06d.tar", maxcount=1000)   # f,g: 1000 rows/tar
for _ in range(per_worker_quota):
    sink.write(build_row(rng, SOURCES, COUNTERS, SEEN))
sink.close()                                                # then: huggingface_hub upload_folder(...)
Throughput. Per soundscape Stage 1 decodes only ~3–8 short files (~tens of ms each) + a tar write; the upload is amortized. 24 cores comfortably produce thousands of packaged soundscapes per hour, bounded mainly by HF upload bandwidth — so one storage server keeps a sizeable GPU fleet fed.

11.2 — Stage 2, in detail (decentralized GPU servers, per shard)

Each GPU server claims disjoint shards with no coordinator — e.g. shard_id % N == my_id, or atomically rename a <shard>.lease file; skip any shard whose annotated output already exists (idempotent, crash-safe). Within a shard it runs three sub-steps, pipelined so the GPU never idles:

Sub-stepDeviceWhat happens
1. caption missing fieldsGPUFor each component lacking source metadata, run the LAION Whisper experts on the isolated component (≤30 s): BUD-E-Whisper_V1.21 (emotion), timbre-whisper, voice-tagging-whisper (style/age/gender) for speech; sound-effect-captioning-whisper for sound/music. Transcript is usually in the source meta; if not, VibeVoice-ASR. Batch all components in the shard for GPU efficiency. (Most procedural clips already have rich source captions → most of this is skipped.)
2. fuse → UAAP dictsGPUGemma-4-12B (unsloth/gemma-4-12b-it-GGUF, llama.cpp) takes the recipe (exact known timings, speakers, overlap, loudness from Stage 1) + the captions/metadata and writes the final UAAP events list — polished emotion/speaking_style strings, dedicated music type, etc. It must NOT alter the Stage-1 timings/speakers (those are ground truth); it only writes descriptions. This is the bottleneck (~tens of GPU-seconds per soundscape).
3. render mixdownCPUExecute the §9 mixer on the GPU box's CPU: place each raw component at its recipe start_time, apply the loudness gains and side-chain ducking, sum, peak-limit, export 16 kHz mono MP3. Runs concurrently with the GPU steps via a queue, so it's effectively free. (Cross-lingual same-speaker turns get Chatterbox VC here if the box has spare GPU, or pre-VC'd in Stage 1.)
# Stage-2 GPU worker. Pipeline: CPU decode/render || GPU caption/fuse.
for shard in claim_my_shards(all_shards, my_id, N):        # decentralized, disjoint, idempotent
    for row in wds.WebDataset(shard).decode():
        rec  = json.loads(row["recipe.json"])
        comps = {r[:-5]: row[r] for r in row if r.endswith(".flac")}
        meta  = {r[:-5]: json.loads(row[r]) for r in row if r.endswith(".json") and r!="recipe.json"}
        # 1) GPU: only caption components whose metadata is missing a needed field (batched)
        feats = caption_missing(comps, meta)               # BUD-E / timbre / voice-tag / sfx-caption
        # 2) GPU: Gemma writes the final event descriptions on the FIXED Stage-1 timeline
        events = gemma_fuse(rec, meta, feats)              # gemma-4-12b-it-GGUF ; timings frozen
        # 3) CPU (concurrent): render the soundscape audio from the raw components per the recipe
        mp3 = render_mixdown(comps, rec)                   # §9 mixer: place + duck + loudness + peak-limit
        push_to_hf(rec["clip_id"], mp3, {"clip_id":rec["clip_id"], **rec["header"], "events":events})
GPU vs CPU balance on a Stage-2 box. GPU = the Whisper captioners (4 small models, batched) + Gemma-4-12B (the dominant cost) + optional VibeVoice-ASR. CPU (run in parallel) = tar I/O, FLAC decode, the mixdown render, MP3 encode, and HF upload. Feed a small prefetch queue so the CPU has the next soundscape's audio rendered while the GPU is still fusing the current one — the ~30 GPU-seconds of Gemma hide all the CPU work behind them.

11.3 — The Stage-1 → Stage-2 row schema (one soundscape = one WebDataset sample)

raw-soundscapes-000042.tar
  └─ soundscape_0041873                       # __key__
       recipe.json     # {clip_id, duration, num_speakers, languages,
                       #  events:[{type,start_time,end_time,gain,loudness,speaker_id,role,

The recipe.json events are the exact ground-truth skeleton (timings, speakers, gains, loudness) computed on CPU; Stage 2 only fills/polishes the text description/emotion/ speaking_style fields and renders the audio. needs_caption per event tells Stage 2 which components actually require a Whisper pass (most don't — the source metadata already has it).

12. Alternative — supercomputer / shared filesystem

If instead you have one big machine with tens of TB of fast shared scratch, collapse the two stages onto it: a CPU partition runs Stage 1 writing rows to a shared directory (skip the HF upload), and a GPU partition runs Stage 2 reading the same directory in place. Same code, same row schema — just a local path instead of an HF repo, with no upload/download churn. Use this when one machine has both the storage and the GPUs; use the two-stage HF design (§11) when storage and GPUs live on separate boxes — which is the case here (24-core storage server feeding a separate GPU fleet).

13. Downstream — the single-pass model we are training toward

The whole point of the dataset: train one model to emit the entire UAAP JSON in a single pass, so we can retire the ensemble. Two training stages:

  1. Pre-train on the millions of procedural soundscapes (perfect labels, free) — teaches the model the format, diarization, multilingual ASR, emotion/timbre/style captioning, SFX & music description, overlapping speech, and full-timeline coverage.
  2. Fine-tune / distill on the ensemble's predictions over real audio — closes the synthetic→real gap so the single model matches (or beats) the slow ensemble on real recordings.

Architecture sketch

┌──────────── 30 s window (×2 for 0–30 s and 30–60 s) ───────────┐ audio ───▶ │ ASR encoder (VibeVoice tokenizer / Gemma audio) [FROZEN or LoRA] │ │ + SFX-Whisper encoder ─▶ projector ─┐ (LAION sound-effect enc.) │ trainable │ + voice-tagging-Whisper enc ─▶ proj ─┤ │ projectors └───────────────────────────────────────┴─▶ LLM (Gemma-4 / Qwen) ──┘ LoRA on the LLM ──▶ UAAP JSON
  • Base candidates: VibeVoice-ASR (7B; great diarization + 51-lang ASR; encoder→Qwen LLM design, so extra encoders project naturally) or Gemma-4 (12B / E4B; natively multimodal, encoder-free audio). VibeVoice is strong at who/when/what but weak on overlapping speech and has no SFX/music understanding — exactly the gaps the extra encoders + data fill.
  • Extra audio encoders → projectors: add the SFX-captioning-Whisper and voice-tagging-Whisper encoders, each with a trained linear projector into the LLM embedding space, so the LLM can perceive non-speech sound, music, timbre and style — abilities the base ASR lacks.
  • What to freeze: keep the ASR encoder frozen (or a light LoRA) to preserve transcription; train the new encoders' projectors + a LoRA on the LLM so it learns the new perception and the UAAP output format without forgetting ASR.
  • 30 s × 2: the Whisper-family encoders cap at 30 s, so process 0–30 s and 30–60 s separately and concatenate/stitch the event lists (re-using speaker ids across windows).

This dataset is the fuel for stage 1. Its breadth (50 languages, overlap, ducked SFX/music, emotional speech, procedural loudness) is precisely what a single model needs to learn perception the base ASR never had.

15. Roadmap

  1. Week 1 — adapters & smoke test. Write per-source streaming readers (return a common Piece(audio, lang, speaker, transcript, raw_caption, fields)); reproduce the §9 mixer on one CPU box; generate 1k clips; eyeball the answer keys with an inspector HTML.
  2. Week 2 — captioning & VC. Wire the 4 Whisper captioners + Gemma-4-12B merge for needs_caption events; integrate Chatterbox VC for cross-lingual same-speaker; validate against the existing scorer.
  3. Week 3 — scale harness. Probabilistic balanced sampler; shard/index/dedup; pick architecture A or B; run 100k clips end-to-end; measure throughput & per-clip cost.
  4. Week 4+ — mass production + training. Generate 1M (then 10M); begin stage-1 pre-training of the single-pass model; then stage-2 distillation from the ensemble on real audio.
